## How to read this matrix

Aliases and full SHAs are in `BASELINE.md` section 2. A citation is `alias@sha7 path:line` or a section. Rows are about the minimum DEMO path, not the full product.

Status rule (applied uniformly):

- `exists`: an executable, tested artefact at a repository ref of record covers the capability at the scope the path needs.
- `partial`: a machine-checkable artefact (schema, configuration example, lint, test, check entry) at a repository ref covers part of it, but nothing executable covers it end to end. A design that is only prose or a proposal does not make a row `partial`.
- `missing`: no machine-checkable artefact at the audited refs. Where a design or proposal exists it is cited in the evidence column and does not change the status.

Result: no row is `exists`. TRON has no runtime code at any ref (B4, B8). The gateway has a tested configuration and lint tool but no order-capable typed service (B13, B14).

Classification (of the proof that closes the gap): `credential-free` (simulated adapter, fake backend, deterministic code, in-memory store, schema and lint), `DEMO-read-only` (needs one read-only DEMO session), `write-approval` (needs the DEMO write-test approval). CA class: the CA evidence item 3 vocabulary, mapped as exists = PROVEN, partial = PARTIALLY PROVEN, missing = MISSING; a cell that could not be checked from permitted sources says UNVERIFIED.

Smallest viable store, by increment (a finding for the PO, not a decision):

- Through the credential-free proofs (INC-03 to INC-07, INC-11, INC-12) and the DEMO read-only increments (INC-13, INC-14): an in-memory implementation behind a journal port is sufficient. Any durable implementation that passes the same journal test suite as the in-memory one satisfies the behaviour; whether it is the TRON-owned Postgres of option A, an embedded store of option B, or something else is R-4 (`RAT@d5f6d32` N-1).
